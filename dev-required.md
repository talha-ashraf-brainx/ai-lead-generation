# Dev-Required Setup

Manual steps only you can do. Everything else is done in code.

Every provider integration always uses the real keys in `.env` — there's no seed/fake-data mode anymore. `DEBUG=true` only affects dev/observability behavior (search result volume, follow-up timing, the dev-only password-reset token, the in-app debug log — see `frontend-integration.md` §11), not which providers get called. That means the items below aren't optional deferred setup; without them the corresponding features simply won't work at all, even in dev.

## Outstanding

- **Phase 5 — Resend, no domain yet (this is why sends show "Failed"):** `RESEND_API_KEY` is set, but there's no verified sending domain, so `RESEND_FROM_EMAIL` stays Resend's shared `onboarding@resend.dev` sandbox sender. Without a verified domain, Resend restricts recipients to **the account's own signup email** or its special `resend.dev` test addresses (`delivered@resend.dev`, `bounced@resend.dev`, `complained@resend.dev`) — see https://resend.com/docs/dashboard/emails/send-test-emails. A send to any other recipient is still *accepted* by the API (we get a message id back and mark the send `sent`), then Resend fails it before attempting delivery — its `email.failed` event means "send error (invalid recipient, quota, etc.)", which is what surfaces as **Failed** with an em-dash in the dashboard's Sent column. Verifying a domain (Resend Dashboard > Domains) and updating `RESEND_FROM_EMAIL`/`RESEND_FROM_NAME` is the fix; it's also the only way to reach real leads rather than just your own inbox.
- **Phase 5 — how sending works meanwhile (no action needed):** because a real lead's address can't be delivered to without a verified domain, `DEBUG=true` redirects **every** campaign send to `DEBUG_EMAIL_REDIRECT_TO` (`debugRecipient.ts`). It defaults to `delivered@resend.dev`, Resend's always-deliverable sink — sends succeed and the whole pipeline (send → status advance → day3/day7 follow-ups) is exercisable, but you can't *read* those emails. **Set `DEBUG_EMAIL_REDIRECT_TO` to the email address you signed up to Resend with** if you want the emails to actually arrive somewhere you can open them. This redirect is debug-only and never applies with `DEBUG=false`, so it can't mask a production misconfiguration.
- **Phase 5 — the API key is send-only:** the current `RESEND_API_KEY` has "Sending access" only, so every read endpoint (`GET /emails/:id`, `/domains`, `/api-keys`) returns `401 restricted_api_key`. That means a failed send's reason can't be pulled programmatically — it has to be read off the dashboard, or the key has to be reissued with Full access (Dashboard > API Keys) to make failures debuggable from code.
- **Phase 5 — Event webhook:** in the Resend Dashboard, create a webhook pointing at `https://<your-api-host>/api/webhooks/resend` subscribed to `email.sent`/`email.delivered`/`email.bounced`/`email.opened`/`email.clicked`/`email.failed`, then put its signing secret in `RESEND_WEBHOOK_SECRET`. Blank is fine for local dev (logged warning, no verification). Works today even without a verified domain — sends from the sandbox sender still fire these events.
- **Phase 6 — Inbound email (reply detection), no domain yet:** `INBOUND_REPLY_DOMAIN` is deliberately **blank** — it must stay that way until you have a real receiving domain. It used to default to `reply.emberline.dev`, a domain that was never registered and doesn't resolve, which put an unresolvable `Reply-To` header on every outbound send (strict receivers reject or spam-file those). Blank means sends go out with no `Reply-To` and reply detection is simply off. Custom receiving domains need DNS you control, but Resend also offers a managed `<random-id>.resend.app` address with no DNS setup (Dashboard > Receiving). To wire this up:
  1. Grab your `<id>.resend.app` address from Dashboard > Receiving and set `INBOUND_REPLY_DOMAIN` to it.
  2. Create a webhook subscribed to `email.received`, destination URL `https://<your-api-host>/api/webhooks/resend-inbound`.
  3. Put that webhook's signing secret in `RESEND_INBOUND_WEBHOOK_SECRET` (left blank, the endpoint still works but skips auth and logs a warning — fine for dev, not for a public deploy).
  4. Once a real domain is verified, switch `INBOUND_REPLY_DOMAIN` to a custom receiving subdomain (Dashboard > Receiving > Add Domain, which adds the MX record for you) instead.

**For reference:** before deploying (Phase 10), swap the local `DATABASE_URL` for a managed Postgres instance (Supabase/Neon/Railway) and set `DEBUG=false`.
